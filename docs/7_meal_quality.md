# Meal Quality

The owner chose meal quality as the next product milestone on 2026-10-14:
the stateless demo stays, and the plans themselves get better. This file says
how quality is measured and what the first measurement found. Each change in
this milestone reruns the measurement and is judged against the baseline.

## 1. How it is measured

`scripts/meal_quality_baseline.py` runs a fixed set of 72 requests through the
real `MealPlanningService` (`backend/app/evaluation/meal_quality.py`):

- 12 cravings × 4 biometric profiles, with no extra constraints;
- 6 cravings × 4 constraint sets (vegan, hypertension, kidney disease,
  celiac) on the average profile.

The profiles span an older sedentary woman losing weight to a large athlete
gaining. Three cravings (`pizza`, `chocolate dessert`, `light soup`) were
chosen to test what happens with no close corpus meal; `light soup` turned
out to have one.

The run is offline and deterministic: no Gemini, USDA or FatSecret keys, and
an empty profile store, so every request also carries the built-in default
profile's restrictions (`dairy-free`, `high-protein`). Two runs produce
byte-identical output.

The calorie model, meal corpus and retrieval backend are always the code's
defaults, never the caller's shell settings. A run stops with an error if the
model or the corpus fails to load, instead of quietly measuring the rule-based
budget or the template meals. Each report starts with what it measured: the
model version, SHA-256 hashes of the model and corpus files, the meal count
and the retriever. Pass/fail is decided on full-precision values, and only
the displayed numbers are rounded (Codex, 2026-10-18).

Per plan it records the plan status, the meal, the calorie target, the
verified calories that ship, their deviation from the target, the scale
factor, and the macro split as each macro's share of the meal's energy.

**The targets (owner, 2026-10-17, DEC-25).** A plan meets them when its
shipped calories are within 10% of the meal target and each macro sits inside
the adult AMDR: protein 10–35%, carbohydrate 45–65%, fat 20–35% of energy.
AMDR is a daily reference applied to one meal. Since DEC-26 the planner
resizes portions to aim for these ranges, 1 point inside each bound, and 2
points when rounding pushes a result out (DEC-28). The service's own 15%
reconciliation tolerance stays as it is: it decides when the service retries,
not whether a plan is good.

**Guardrails** (Codex, 2026-10-18). Until DEC-27 all 72 default plans were
`matched`, and the default set still never reaches a refusal. Five
guardrail cases do, each with its outcome fixed in advance. They run through
the same service against a controlled corpus,
`backend/app/evaluation/guardrail_meals.json`: three meat meals copied from
the shipped corpus before DEC-28 and kept as they were, so a vegan request finds no safe corpus meal. One case is
a matched control, two must fall back to a named template, and two (vegan,
soy allergy and kidney disease) must be refused as infeasible. They are
reported in their own section and never counted in the 72, so the default
set's numbers stay comparable from one change to the next. The script exits
1 when a guardrail does not hold.

```bash
uv run python scripts/meal_quality_baseline.py                      # Markdown report
uv run python scripts/meal_quality_baseline.py --json out.json      # plus rows as JSON
```

## 3. What the baseline shows

1. **Calories are on target; macros are not balanced.** Fixed 2026-10-18:
   per-ingredient balancing (DEC-26) brought 41 of 72 inside AMDR, and a
   cooking fat in the six recipes that had none (DEC-28) brings all 72. The
   rest of this finding describes the baseline. Every plan lands
   within tolerance, but only 11 of 72 have all three macros inside AMDR.
   Carbohydrate is low in 46 plans (under 45%), protein high in 40 (over
   35%), fat low in 34 (under 20%). Some meals are skewed the other way:
   Salmon Quinoa Plate is 46% fat and Chickpea Curry Bowl 70% carbohydrate.
   Part of the protein skew comes from the default profile's `high-protein`
   restriction, which favours high-protein meals in ranking (inferred from
   the retriever's preference bonus, `rag/retriever.py`).
2. **Off-menu cravings get an unrelated meal instead of the fallback.**
   Fixed 2026-10-18 (DEC-27): only relevance to the craving, without the
   profile's bonus, decides whether the corpus has a match, so these 11
   requests now fall back with a "no close match" warning. The rest of this
   finding describes the baseline. `pizza` and `chocolate dessert` are served Chicken Fried Rice for every
   profile, with no matched terms, at a score of 0.198. That clears the
   retriever's 0.16 threshold only because of the preference bonus from the
   default profile's restrictions, so the deterministic fallback is never
   reached. Three constrained requests are similar: vegan `salmon dinner` and
   `high-protein burger` get a tofu noodle bowl, and kidney-disease
   `spicy curry` gets a turkey burger bowl (scores 0.18–0.19).
3. **The meal target ignores the extremes.** The target is 28% of the daily
   budget, clamped to 350–850 kcal. The large athlete's budget is 4,521 kcal,
   so its meal is capped at 850 (19% of the day). The older woman's 350 kcal
   floor was 36% of her day before the calorie floor below, and is 29% now.
4. **The smallest daily budget was too low. Fixed 2026-10-17 (DEC-24).**
   986 kcal for a 62-year-old, 52 kg woman losing weight was expenditure minus
   a fixed 400 kcal, with no floor. A weight-loss budget now stops at 1,200
   kcal for women and 1,500 for men, never above expenditure. Her budget is
   1,200 kcal. Her meal target stays 350 kcal (28% of 1,200 is under the 350
   floor), so no plan in the baseline changed.
5. **Calorie accuracy is measured against local tables.** Offline, 68 of 72
   plans have at least one ingredient whose macros are estimated. So the
   tolerance result says the planner is consistent with its own tables, not
   that the meals truly have those calories. A run with a USDA key would
   test that, but it would no longer be deterministic.

## 4. Suggested order of work

Each item is a separate PR that reruns the baseline and reports the change.

1. **Macro-aware selection and scaling** (finding 1). Scaling is done
   (DEC-26): each ingredient gets its own portion factor. Selection was
   measured and ruled out (DEC-27): every meal that would meet the targets in
   place of a missing one is less relevant to the craving. The recipes that
   could not be balanced now have a cooking fat (DEC-28), so this is done.
2. **Relevance gate on craving terms** (finding 2). Done (DEC-27).
3. **Corpus growth** (`4_next_steps.md` §7.9), aimed at the gaps the baseline
   shows: balanced vegan mains, kidney-safe options, and the cravings with no
   match today.
4. **Meal target at the extremes** (finding 3), once the owner decides how
   many meals a day the target assumes.
